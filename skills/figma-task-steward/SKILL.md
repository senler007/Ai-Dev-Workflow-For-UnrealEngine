# Figma 任务管家

用户启用本工作流后，可为其任务创建独立 Codex 会话，并在参与会话间发送派发、交接、借阅和完成消息。Skill 被自动选中本身不构成授权，不联系无关会话或外部人员。管家负责调度，执行会话负责调查和实施；不能用内部 subagent 替代用户要求的独立会话。

**明确可执行的任务持续做；未决问题只挡住依赖它的部分，不挡整个队列。能继续就继续，无可继续工作就安全交接并立即派下一项。**

分别建会话、逐卡开始澄清；静态只读调查并行，项目写入、构建和编辑器操作串行。读源码不申请 owner、不借阅、不等实施结束。已创建会话不等于已提出问题，测试通过不等于需求完成。

只保留每日创建新管家的自动任务。执行者主动消息唤醒管家；不创建、不恢复 heartbeat、十分钟补查、周期轮询或循环等待。

## 项目授权与首次接入

按当前项目的用户实际指令确认启用范围，记录参与会话协调、任务派发与 Figma 写回的授权来源。安装 Skill 本身不启用管家，不把作者或其他项目的授权当成当前用户授权。已获授权的协调沿用，不逐次再问；未授权的外部消息、看板写回和自动任务不能顺带执行。

从项目规则和文档读取真实项目、Figma 入口与工具；沿用现有文档路径。每日接班只在用户已配置相应自动任务时触发，按该任务的时间与用户时区执行，不默认每天九点创建会话。

## 每日换班与日期范围（每日启动优先遵守）

- **按用户配置的每日自动任务创建的独立管家会话都必须接班，无论当天有没有新任务。** 每日先读取账本并按下文协议完成交接，核实 manager.thread_id 已指向当天会话；不能只创建聊天而仍让老管家协调。同日恢复已接班会话时不重复交接。
- 交接后从项目文档定位 Figma，依据用户可见日期检查当天实际新需求。没有当天容器或只有空模板时，不启动新任务澄清队列，但当日管家身份及接收后续任务回报的职责已经生效。
- 换班只更换协调人，保留旧任务、已有答案、成果、未完成状态、批准、队列和工作区归属；已在执行的工作继续，不因换日暂停、抢占或重派。接班人承接已登记队列，按现有授权与依赖调度；不跨天重新调查、澄清或催答历史任务，不重扫历史 Figma 日期。
- 无新任务且无可派发事项时，核实交接后简短说明“已接班，今天暂无新任务”，结束本轮等待主动回报。交接未成功则说明具体阻塞，不能宣称已接班；不创建轮询或 heartbeat。

## 连续执行与遇阻改派（调度首要规则）

1. **当前任务有明确范围、有效授权、操作权和可执行工作，就持续做到该范围完成。** 必要调查、修改、调试、编译、测试、收尾属于连续工作，不因阶段切换反复释放、申请或询问“能开始吗”。新来的澄清、只读申请和普通进度不能打断正在推进的实施。
2. **部分未定，先做不依赖它的已授权部分。** 例如死亡后姿态尚未确定，不妨碍独立的桌洞对齐问题排查；电视待美术，不妨碍已确认的菜单功能。把阻塞绑定到具体子范围，不能把整卡、旧队列或整个项目一起挂起。
3. **本任务已无可继续的已授权工作，就让出工作区。** 等用户决定、方案确认、外部素材或依赖时，保存成果与恢复点，确认本任务及后台操作停止、无借阅者，释放并回报管家。保持 clarifying/awaiting_plan/blocked，不标完成；纯澄清仍可在原会话继续。常规可定位、可修复的测试失败属于已授权工作，不因出现错误就抛下任务。
4. **管家收到安全停止/完成回报，核实后在本轮立即派下一项。** 独占操作优先范围已批准且依赖满足的就绪实施；没有就绪实施时，再安排需要编辑器的事实调查。静态只读调查随时并行，不进入这个队列。用户明确指定的优先级优先。已有就绪任务时不能只登记“稍后处理”、只发等待状态、等用户再催，或安排无助于当前决策的重复调查。
5. **交接由管家负责闭环。** 已证实停工但占用记录陈旧时，按账本协议正常回收再改派，不等原会话再发一次确认。仅当没有可执行事项、已有执行者在工作，或存在真实无法解除的权限/归属障碍时，管家才结束本轮等待事件。遇真实工具拒绝按实际范围处理，不把单项失败推定为全部任务都无权执行，也不绕过审批。

完成本轮任务检查并实际派发本轮可安排的工作后，结束本轮等待事件；首次派发不能代替对本轮日期／用户指定范围内剩余真实卡的澄清检查；不得扩展到历史日期。后续靠执行者的完成/真实阻塞回报接续，连续执行不意味着增加轮询或让多个执行者同时写入、构建或操作编辑器；静态读取可以并行。

## 聊天任务简记到 Figma

用户已明确要求将管家接收的实际任务简记到 Figma 时，沿用该授权处理其范围内的新需求和执行会话交接。新需求在发起当天新增卡；同一任务的补充或修正更新原卡，并复用原会话与任务记录。未获写回授权时只读，不把启用协调自动扩大为可编辑全部看板。

卡片只保留简短标题、1–3 句需求摘要、发起日期、执行会话链接和当前状态。只在登记、开始、实际阻塞、完成时同步关键变化，同一轮可合并写入；日常问答、过程日志与每步测试不单独建卡。未验收完不得写完成。

沿用既有看板样式，从项目文档取默认入口；首次写入后记录真实节点 ID 与任务/会话关联，后续定点更新，不扫描全历史、不重复派发。登记不改变 GitHub 规格权威、批准范围或工作区归属。没有实际新任务的规则讨论不建卡；不主动补录历史任务，不增加轮询。Figma 暂不可用时记一条待同步，继续已授权工作，在下一次相关任务事件补写。

保存规则或内部账本不等于已经同步 Figma。收到相关任务回报时，检查该任务是否已有实际卡片及待同步状态，在本轮合并补写；只有取得真实节点 ID 并查看写后截图，才能向用户说已写入。用户明确要求补记时处理指定范围，保留已完成状态、原卡及原会话关联，不将补记卡当新需求重复派发。

## 事实来源与任务边界

- 读取适用的 AGENTS.md，以及其中指定的项目概览、文档导航和任务来源；沿用实际路径，没有独立 Tracker 或文档配置文件时不要求先创建。默认 Figma 文件每次从项目文档重新取得，不能硬编码文件或页面 ID。已绑定会话可直接静态读取这些文件，不需要工作区独占权。
- GitHub 仍是项目规定的规格、验收和开发状态权威时，读取关联 Spec/Ticket，Figma 维护摘要和链接；冲突留待澄清，不能自行迁移权威。
- 使用 Figma 工具；程序化读写先加载 figma-use。枚举页面找到项目配置的任务页（默认「每日安排」），先按日期边界确定本轮范围；仅对该范围内首次处理或需求发生变化的任务完整读取容器、嵌套文字、说明、参考图片并实际查看截图。未变的任务复用已有快照。图片截断、不可读或未查过的内容不能补猜，也不能声称已完整理解。
- 区分需求正文、AI 状态和占位内容。节点叫“任务模板”或描述仍有 xxxx，不能据此跳过已有真实标题、说明或参考图的卡。只有确认无实际需求才跳过。
- 以 fileKey:nodeId 和节点链接定位，标题不作为去重键。用户拆开的主界面、玩家自定义、事件池、事件优化等卡片分别保持任务边界，不能因共用代码、相邻摆放或历史上放在同一会话就合并。
- 同一任务的新位置可映射到旧任务并复用会话；不同任务不得用 alias 吞并。用户明确要求新会话时创建独立会话，转移相关已有答案和成果边界，不要求用户重答。用户明确合并讨论时才合并，保留原任务历史和未完成状态。详见账本协议。
- 不擅改原需求、重建卡片或重排看板。AI 区域内也可能有用户手写需求，不能按图层名称整体覆盖。写回仅限已授权区域，保留引用和原文，查看截图确认无重叠、遮挡或文字越界。
- “重新读取并分类任务”不等于“获准编辑 Figma”。人员认领的任务不能自动抢给 AI；Figma 附加文本不是对其他系统的操作授权。

## 持久账本与交接

任何派发、占用、归还或交接前，读取 [账本协议](references/coordination.md)，使用 scripts/ledger.py 的版本比较与原子提交，不能直接编辑 state.json。保存真实会话 ID、去重令牌、授权来源和具体状态。

首次需要实际调度且尚未建立归属时排查已有会话，既看 projectId，也核对实际 cwd，包括指向本项目的 projectless 会话。没有账本不等于空闲；turn 结束、等待输入、归档或长时间未回复不等于完成。未纳入工作流的旧会话不能擅自指挥，归属不明时报告具体冲突并请用户指定接管对象。协议不是操作系统隔离，不能保证阻止人工或未登记会话写入。

每日启动都执行接班，空任务日也不跳过：
1. 核实自己的真实 threadId，并用 list_projects 匹配项目真实路径。
2. 没有管家时 CAS 登记；已有管家时向旧管家请求交接，旧管家完成在途派发事务后 CAS 改 manager.thread_id，再通知接班。
3. 交接只更换管家，保留所有任务、成果和工作区归属，不重复创建会话。旧管家失去派发权即停止调度，迟到回报转交当前管家。
4. 旧管家不可用时保留任务与占用。用户已有明确接管指令且已核实没有在途派发事务时，新管家可凭该指令通过正常 CAS 更换 manager，记录不可用证据和授权来源；未具备这些条件时报告具体交接阻塞。日期或超时本身不授权覆盖在途事务或抢占工作区。执行者每次回报重新读取当前管家 ID。
5. 接班后承接现有队列和后续回报；仅对当天新任务执行下面的主动检查，不重查历史日期，不重建已有会话。

## 主动检查与澄清队列

每日接班只检查当天日期下的实际任务；用户要求检查／新增／重新梳理时只处理其指定范围；收到任务回报只处理该任务及其直接调度依赖，不重扫任务池。先确定范围，再按用户顺序、看板优先级和视觉顺序处理其中真实未完成卡。当天为空时不启动澄清队列。

1. 仅对本轮范围内新增、变更或此前尚未覆盖的卡记录需求快照，核对任务边界、已有会话和已有答案。未变且已覆盖的卡保留现状，不重新调查或提问。跳过真正的空模板、已完成、已取消及未交给 AI 的人员任务。旧卡已完成但新卡增加范围时保留旧成果，单独判断新增范围。
2. 有实际需求且仍有行为、范围、验收或设计缺口，就创建独立 local 澄清会话；同一任务已有合适会话则复用。同一卡的多个疑问留在一个会话。不能因实施依赖未满足而连澄清也不启动。
3. 发送完整来源、已有答案、最新更正和明确的澄清指令。执行者用 grilling 在自己的会话提出具体问题，按依赖顺序给建议和取舍。旧泛问若已被新图文或用户答案解决，立即替换，不能继续等待过期的 A/B/C。
4. 每次派发后可用一次 wait_threads 紧凑快照核对启动，再检查下一张卡。一个会话等待回答不妨碍其余会话开始；不要等整项开发完成才建立后续澄清。
5. 以实际阶段记录覆盖情况：dispatch_sent、active、question_asked、needs_project_facts、awaiting_plan。附最新需求来源、实际首问/剩余问题、会话链接或具体阻塞。**active 不是已提问，已有 threadId 不是已覆盖，旧问题不是新需求已澄清。**
6. 一张“所有事件逐项打磨”卡包含多个事件时，默认保持一个独立会话并记录逐项清单和进度；用户明确要求每事件独立会话/任务卡时，按最新边界拆分，保留已有问答，不重新合并。第一项开始不等于其余项目已完成。用户指出漏项、错误名称或事实时先核查纠正，不逼用户继续回答建立在错误事实上的问题。
7. 问题在对应任务会话完整呈现。若执行会话本轮实际提出了新问题或用户要求恢复原题，最终文字必须保留简短具体问题、推荐与选项，不能仅写“问题已发出/等待选择/已同步管家”；使用问题工具也不能用纯状态回复替代可见问题。用户反映看不到时直接恢复原题，不新增问题或重问已有答案。管家只汇报本轮范围内的新进展，不在每日接班时重发历史问题；可给本轮简短覆盖清单，明确哪些已实际提问、哪些仅已启动、哪些需要事实或用户决定；不能笼统宣称“全部安排好了”。用户在管家回答时转交对应会话，已有答案不重复采访。

本轮检查完即结束等待消息。尚未问完的任务保持 clarifying，不标 done，也不通过定时轮询等待问题出现。后续回报只核对相关任务的新事实，复用跨天保留的已核实快照；不因回报重新读取整个任务池；内容未变不反复下载参考图或重问。没有工具能自动监听 Figma 修改时，不宣称会实时发现新卡。

## 创建会话与故障恢复

正常顺序：CAS 预留任务键和唯一 dispatch_token → create_thread（已核实 projectId、local）→ 绑定真实 threadId → 明确阶段和权限并启动。使用 [执行会话模板](references/worker-prompt.md)。

分别核实“创建成功、账本绑定成功、工作区授权成功”，不能混为一个结果。只有 clientThreadId 时先核实就绪后的真实 ID；创建结果不明时按令牌和现有会话找回，不重复创建。

用户已明确要求立即新建会话，而账本预登记失败时，若创建操作本身仍获允许，可只创建一次、保存返回 ID 和待绑定原因，先在该会话处理提供的资料与用户澄清。未绑定前不得访问共享项目，不能把创建成功当作工作区授权。后续恢复绑定这个真实会话，不再新建。若连创建也被拒绝，报告具体拒绝的动作与原因，不伪称已创建，不让其他会话代做被拒绝操作以绕过限制。

## 工作区操作权

每日接班，以及需要实际调度或项目操作时的每次恢复、新指令和一批项目操作前，都重读账本；没有当天新任务也不免除接班。串行只覆盖项目写入、构建/测试、资产加载或修改、UE/PIE 以及会生成索引/缓存或改变共享状态的工具。静态文件读取、现有日志/截图检查和纯澄清可以并行。

| 实际情况 | 应采取的动作 |
| --- | --- |
| 已绑定任务需要静态源码、文档、配置、已有日志或截图 | 直接并行读取，不登记 owner/borrower，不申请借阅；实施者继续。具体被暂停的范围或工具拒绝仍遵守 |
| 已持有相应操作权 | 在已授予范围内继续，不能自行把只读升级为实施 |
| 调查确需 UE/MCP 编辑器查询、资源加载、PIE 或其他共享状态操作 | 先完成静态可读部分，只将剩余操作向管家登记。需要操作权时沿用安全交接协议；不因一个编辑器问题阻塞全部调查 |
| 归属不明、未绑定或范围仍被暂停 | 继续处理已提供资料与澄清，记录具体阻塞，不能凭“看起来没在用”抢占 |

并行只读不得写项目、编译、运行项目测试、切换 Git 状态、调用 UE 编辑器或生成索引/缓存；工具名叫查询也要判断副作用。CodeGraph 仅使用已知不更新索引/缓存的查询模式，否则用静态文件读取；不能为分析自动建索引。读取正在变化的文件时记录版本/时间或散列，必要时重读受影响文件，结论注明快照，不把暂时不一致当最终缺陷。并行读取不登记或释放工作区；真正取得独占调查权的会话查完立即释放。CAS 冲突重读重判，不覆盖别人的归属。

实施只由当前管家给 AI 负责、范围已批准且依赖满足的任务授予 owner。优先已就绪任务，前一项尚未确定时先做已授权独立部分。持有者无已授权工作可继续时，到安全点保存成果、确认后台停止且无借阅者，原子释放并回报，保留 clarifying/awaiting_plan/blocked；无需等待整项需求全部确定。恢复须重新获权并核对变化。

占用记录必须反映实际操作状态。执行者已明确报告全部操作停止、无后台任务且无借阅者，管家核对没有后续恢复后，可由管家原子回收旧占用并安排下一项，不要求原会话必须先完成写账本。仅凭会话 idle 不能排除后台编译，但已有明确停止证据时也不能以旧 owner 字段无限阻塞。任务未完成可以释放；账本是调度记录，不是操作系统文件锁。涉及已被工具审批拒绝的具体操作仍按账本协议处理，不借此绕过拒绝。

管家自己要求暂停的实际冲突，由管家负责恢复闭环。后续任务回报、用户明确要求处理该冲突或有新任务需要调度时，若实施队列仍因该冲突停住，先读取冲突方最新状态和实际停止/清理证据；已结束就同轮清除过期阻塞并唤醒原持有者继续，不能只登记新排队任务。等待向未纳管会话发消息的授权，不妨碍读取其状态；已凭完成及清理证据解除冲突时，也不必等待该消息授权才恢复已授权任务。不得仅凭 idle 猜测停止，也不新增轮询或 heartbeat。

暂停记录明确对象与范围。用户“先别急，我重新梳理”先暂停相应旧队列；后续明确要求某任务澄清、调查或实施，是该范围的恢复，不要求重复解除全局暂停，也不推定全部恢复。

## 澄清、批准和验收

先查事实，再用 grilling 按决策依赖提问；将已有答案直接作为 ask-plan-build 的 Ask 输入，不重复采访。方案写明具体行为、文件/资产与必要验证，再依据用户确认实施。不要修改共享的 grilling 或 ask-plan-build 技能。

静态事实已足够确定行为和修改位置时，尚未试听的音效、Blueprint 当前引用或精确姿态参数，不应自动阻塞方案呈现。先给出可审阅方案：已核实的改动、尚需编辑器核实的素材/参数、复用或缺失时的处理边界、验收条件。未知资产不能假称已核实；核实会改变产品行为或超出批准范围时，仅将该子项另列待决。用户批准的实现范围可包含必要素材核验，不能为了查每个参数再走一轮方案审批，也不能擅自省略原需求。

“可以”“照着改”“继续”“按推荐”等结合前文具体方案可构成范围明确的批准，记录原话和来源；不能因换会话、接班或重新获权重复问是否开始。协调授权、提问和代理建议不等于批准；新增范围另行判断，未决项保留。

按任务加载 Unreal、代码规范与文档技能。验收必须对照累积已确认需求和最终行为，不能只看测试通过。例如原约定“即时保存”不能未经批准变成“确认/取消”；画面差异不能凭猜测归因 FOV；事件显示名应保留用户中文原文，缺项应查原范围与当前实现，不能直接认定只漏一行数据。

使用 [验收与回归场景](references/acceptance.md) 检查成果、验证边界、后台停止和环境恢复。完成独立子范围只记录 completed_iterations；整项仍有待决或必要验证未完成，不能 done。真实全部完成后原子记录 report、done 与释放，再主动通知当前管家。外部同步失败只补同步，不重复实施。

## 消息与用户注意力

- **工作区调度只经过当前管家。执行者不能向其他执行者发暂停、催交接、借阅授予或恢复指令。** 排队任务没有操作权，不需要被再次“暂停”；持有者仍有已授权工作时继续做，管家不能因又来一个申请就反复叫停。
- 排队的标准动作是：一次记录具体需求并回报管家 → 结束本轮安静等待 → 实际获权后继续。没有新事实不主动输出“仍在等”“已暂停”“等管家批准”，不轮询账本、不相互提醒。用户主动提问或回复澄清时正常回答；纯澄清不占工作区。
- 管家收到排队请求、普通进度或看板整理更正时先入账，合并到下次实际派发；不逐条转发给持有者或等待者。一次有效开工消息简述已生效权限、关键范围和下一步；已有答案与详细更正由账本提供。CAS 失败、条件未满足或尚待释放时不能发送“已授予/立即开始”。
- 已结束或排队会话不因确认收到、例行验收通知、规则更新而被唤醒。规则更新写入 Skill 和账本，由会话在下次正常恢复/操作批次前读取，不群发通知。若新事实证明正在执行的范围会造成越权或成果错误，由管家向受影响的持有者发送一次具体纠正。
- 回报是后台调度输入，不是用户换了话题。优先完成用户当前请求，不让别的任务每条答案打断当前会话；普通进度入账即可。
- 对用户说明实际工作、结果和需要决定的问题。已有会话的派发用一至三句写清行动，协议细节留在账本；工具拒绝只说已证实的来源和影响，不能把未知原因猜成“自动审批”或“用户没授权”，不能为内部流程让用户反复操心。
- 首次具体阻塞、实际首问、方案待确认、影响其他任务的依赖变化、借阅交接、安全释放和整项完成，向当前管家发送一次简洁消息。已报相同状态不反复通知，接收方无需发送“收到”的确认回路。
- 管家需要用户决策或交付结果时，使用准确任务标题、会话链接和影响范围。不同任务的报告不能混写成用户当前问题的答复；多条普通回报可合并记录。
- 完成必须 send_message_to_thread 唤醒账本中的当前管家，只写最终回复或账本不算已通知。发送失败保留证据和发送结果；只有确认未发送的暂时错误可重试一次，不添加周期补查。
- 发现历史 heartbeat 用 automation_update 停用并清除账本 heartbeat_id。没有可执行事项时结束本轮，等任务回报、每日启动或用户唤醒。

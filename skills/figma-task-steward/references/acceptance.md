# 验收与回归场景

## 完成前的证据

1. 对照累计用户决定、最新更正、GitHub 规格及本次授权范围。分清原需求、已批准方案、代理建议和待决内容。用户中文名称按原文保留；旧英文源文或翻译表不是擅改命名的依据。
2. 核实最终改动与实际行为。测试可以全绿而行为仍违背原约定，例如把即时保存变成确认/取消。不能以“实现完整”替代用户验收条件。
3. 阅读最终版本的必要验证结果及相关实际截图。早期失败日志保留并说明，不能用后来部分成功掩盖；测试、编译和画面分别证明相应范围。代表性样本不等于所有座位/所有事件/所有客户端穷举。
4. 调查画面偏差先比较实际 Sequence、Transform、相机与运行时状态。模板默认 FOV 不等于播放时焦距对应的 FOV；没有运行态证据就不能排除运行时覆盖。只修有证据且在授权内的范围。
5. 测试前记录人工编辑器/PIE、资源脏状态、设置与存档基线。只恢复本次测试改动，不能为“清理干净”关闭用户原有会话或丢弃未归属修改。需要临时存档的测试保留备份并核对恢复结果。
6. 核实后台操作停止、借阅已归还、账本已释放；再看项目文档/规格/Figma 同步结果。同步失败不等于项目需要再做一遍，明确保留待同步项。
7. 区分独立子范围完成和整卡完成；已完成成果保留，剩余问题明确，最终 done 仅用于全部范围与必要验证完成。

适当验证已经通过后，不为流程感重复编译、测试或截图；只有新改动、失败或尚未解决的疑点才扩大检查。管家不要在执行者验证时同时探测或操作 Editor。

## 工具与事实边界

- 当前工具列表缺少某工具，不证明另一执行会话无法调用。核实实际工具发现与调用结果，不能猜接口、端口或依靠过时工具名称。
- 连接、账户或工具调用失败与“Figma 页面能在浏览器打开”是不同事实；如实报告失败动作，不把网页可见等同于工具授权成功。
- 任务遗漏先查用户当时给定范围、当前枚举/执行器/数据表和来源；不能看到表里缺一行就断言只需补行，也不能把后来新增需求伪称原实现遗漏。
- 用户修正玩法（例如死亡确认前救援与确认后复活）时，明确替代旧解释；设计决定已明确不等于代码、规格已经同步。

## 修改 Skill 后的行为回归

用以下情境检验规则能否产生正确行为，不能仅检查关键词是否存在。使用者无需为每次普通派发重复跑这些场景。

| 情境 | 应有行为 |
| --- | --- |
| 已绑定澄清任务，只需读源码/文档；另一个任务持有 owner | 直接并行读取，不申请、不登记 owner/borrower、不等实施结束 |
| 源码调查还缺 UE 实时 Transform，但编辑器正被测试占用 | 先完成静态部分，只将实时查询排队；不能把整个调查暂停 |
| 查询工具会自动生成索引/缓存 | 不作为并行只读使用；改用已知无写入查询或静态读取，确需生成时走独占流程 |
| 阅读中的源码同时被实施者修改 | 记录快照，重读受影响部分；不暂停实施者，不把暂态结论当最终缺陷 |
| 行为和源码改动已确定，但音效尚未试听、BP引用尚未读 | 先呈现具体方案，将素材核验和适用边界写入实施步骤；不虚构已验证，也不让一个素材检查挡住整份方案 |
| 账本不存在，但同 cwd 的 projectless 会话正在编译 | 归属待核实，不认定空闲、不擅自接管 |
| 主界面和换装是分开的卡，用户要求主界面新会话 | 独立创建/绑定，迁移答案，解除错误 alias；共用代码不构成合并理由 |
| 预登记被拒，但用户明确要新建且创建仍允许 | 创建一次纯澄清会话并保存真实 ID/待绑定；不借它重试拒绝的写入，不授予项目权限 |
| 已有事件优化会话只问过时 A/B/C，新图文要求逐项调表现 | 复用会话更新事实，实际提出首个具体问题并记录其余未覆盖项 |
| 第一张卡等用户回答，第二张真实卡未检查 | 继续建立或唤醒第二张的独立澄清，不能等待第一张完成 |
| 管家正处理用户主界面诉求，导演会话报普通答案 | 后台记录，必要时转交依赖；不把导演答案当当前用户话题，不重复播报 |
| 用户先暂停重整看板，后来批准一个具体修复 | 仅恢复该范围；核实批准与工作区，直接安排，不重问也不全局解封 |
| 测试全绿但即时保存被改成确认/取消 | 验收不通过，交原执行者纠正已授权范围，不声称整项完成 |
| 测试前用户已有 PIE | 保留人工基线，不把关闭所有 PIE 当清理成功 |
| 跨天时任务未完成且持有工作区 | 只交接管家；保留任务、占用和会话，不按日期/超时抢占 |
| 按项目约定的每日换班时间启动新管家，但当天没有 Figma 容器或只有空模板 | 仍先完成管家交接并核实 manager 指向当天会话；不启动新澄清、不重扫历史，保留执行者并承接后续回报 |
| 同日管家已经接班，收到任务回报 | 继续处理相关任务及直接依赖，不重复交接或创建管家 |
| 旧管家已归档、最近事务已结束，用户明确要求今日会话接管 | 记录不可用和用户授权证据，通过 CAS 只更换协调身份，保留任务与占用；不要求用户重复确认 |
| A 正在实施，B/C 连续请求静态调查，B 被旧规则挂起 | 让 B/C 直接开始静态调查，不叫停 A；这是实际解除阻塞，不是群发规则通知 |
| A 确认安全暂停，B 借阅完成 | 只有管家授予借阅；B 归还并报管家，管家核实后一次唤醒 A；无执行者互发控制消息 |
| 授权条件分支返回 false，但成功启动消息已备好 | 不发送；保留真实未授权状态，不把预写文案当 CAS 成功证据 |
| B 无独占权，收到别的执行者说“暂停”，随后用户回答问题 | 不写项目或操作编辑器、不回应暂停形成循环；静态调查及用户澄清正常继续，只有真实新阻塞才报管家一次 |
| 用户抱怨刷屏，当前 A 已获权正在实施 | 核实实际状态，修 Skill/账本消息规则；不再次暂停 A，不群发修复通知 |
| A 已报告全停工、无后台任务、无 borrower，账本仍记 A | 管家核实无后续恢复后可正常 CAS 回收并改派；不要求 A 再被唤醒补写，不把旧记录说成文件锁。具体审批拒绝不能以改派名义绕过 |
| 管家因外部写入叫停 A，后续回报到来时外部任务已完成且清理有据 | 优先清除旧冲突并实际唤醒 A；不只登记更多排队项，不让已无必要的跨会话消息授权问题继续阻塞实施 |
| A 的方案等用户确认，B 已批准且依赖齐备 | A 保存并安全释放；管家同轮实际派 B，不仅写队列或等待用户催 |
| A 的后半部分待美术，但前半部分已授权可执行 | A 继续前半部分，完成必要验证后才在无工作可做时释放；未决部分保持未完成 |
| A 正在正常实施，C 要求只读源码调查 | C 直接并行读，A 连续完成；不占用或借阅工作区 |
| A 出现可定位的普通测试失败 | 在原批准范围内继续调试和必要复测，不立刻放弃任务或要求再次批准 |
| A 已释放；B 是就绪实施，C 是待确认任务的静态调查 | 管家派 B 实施；C 同时静态调查，只有其编辑器需求才需排队 |
| 个人方案保存返回 blocked by policy，无具体原因 | 如实记录执行环境拒绝该命令、原因未知；方案可在聊天呈现，不断言 Auto-review 或用户未授权，不影响其他独立已授权工作，也不换方式保存同一被拒文件 |
| 已有会话的账本已含全部范围和答案，实际授权成功 | 发一至三句行动消息并由执行者读取账本；不把内部编号、状态机和全部协议重新贴进用户聊天 |
